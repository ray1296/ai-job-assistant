# 模型微调：先做 RAG Query Rewrite，再做工具路由

## 本项目最值得微调的功能

优先级从高到低：

1. **RAG Query Rewrite / 检索查询改写**（最推荐）
   - 输入：用户原问题 + 当前科目/方向
   - 输出：一个自包含检索 query + 3~5 个关键词 + 可选方向过滤
   - 解决：短 query、指代（“它/这个”）、口语化、同义表达导致的召回失败
   - 评测：Recall@k、MRR、引用正确率、拒答率，完全离线可测
   - 风险低：模型只改检索词，不直接面向用户生成事实
2. **工具路由器**（工具数量增长后再做）
   - 输入：用户请求
   - 输出：工具名 + 参数 JSON 或 none
   - 现在已经用 Tool RAG 把工具表缩减到 1~3 个，4 个工具时收益有限
3. **面试评分/追问策略**（有标注数据后再做）
   - 需要人工评分样本，涉及公平性和高风险，不建议先做
4. **简历定制文案风格**（不建议先做）
   - 事实校验已经在服务端做；微调模型仍可能改写数字/技能，风险高于收益

**结论：先做 RAG Query Rewrite，不把完整工具表训进模型。** Tool RAG 已经解决工具表变长/更新问题；微调只做“检索查询改写”这类窄任务。

## API 微调是什么（不是给每个人一台服务器）

- 基础模型（如 Qwen3.5-9B）运行在云厂商的共享推理集群上。
- 微调训练会产出一个**属于你的模型产物**（全参权重或 LoRA adapter），存在“我的模型”里，不是把公共模型改掉。
- 调用时通常有两种形态：
  - 云厂商提供公共池/托管 endpoint：你的模型 ID 走共享推理资源，逻辑隔离；
  - **专属部署**（阿里云 DTU/MU）：给你独立的 GPU/TPM，物理隔离，按月预付费，适合稳定生产。
- 你的网站所有用户共用**一个**微调模型 endpoint；不是每个用户一个模型。
- 微调模型不是训练完自动替换公共 qwen-plus；要部署/发布后拿到模型 ID，再改 gateway。

## 工具路由为什么不做主方案

把「完整工具表」直接塞进模型权重，不是 2026 年做 Agent 的主流方案，原因：

1. 工具 schema 会变，微调一次就过期；
2. 模型会「记住」旧工具名，运行时反而更容易幻觉调用不存在的工具；
3. 工具参数校验、权限、幂等必须在服务端做，不能交给模型权重；
4. 原生 function calling / 工具检索 / prompt caching 更便宜、更可控。

更合适的做法是：**微调一个小型工具路由器**，只负责「用户这句话该选哪个工具 + 抽参数」，真正的工具 schema、权限、参数校验仍由服务端提供。这样既减少每次塞完整工具表的 token，又保留可变更能力。

## 阿里云百炼 SFT

当前北京地域 Key 已能访问：

```text
POST https://dashscope.aliyuncs.com/api/v1/fine-tunes
```

（探测返回的是 “Missing training files”，不是 401，说明鉴权通过。）

正式训练前需要确认：

1. 在百炼控制台确认可用模型（如 Qwen3.5-9B / Qwen3-8B）的 SFT 高效训练权限；
2. 训练集格式和最小条数符合控制台要求；
3. 训练时长、费用、部署后的模型 ID；
4. 训练完成后的模型是否支持 OpenAI 兼容调用。

## 推荐执行顺序

1. 先保持线上 function calling + 工具表（现有逻辑），不动；
2. 用 197 条样本做一次小 SFT，产出 `tool-router` 模型；
3. 只把「路由」切到微调模型，工具执行仍走现有 `server/tools.mjs`；
4. 用固定 100 条评测集比较：工具命中率、参数正确率、无工具误触发率、延迟、token；
5. 达标再切换，保留原路由作为 fallback。

## 备注

- 不把简历、投递记录、聊天内容、上传文件放进训练集。
- 不把工具执行权限下放给微调模型。
- 真正训练会产生云端费用和训练时长；先报预算再跑。
